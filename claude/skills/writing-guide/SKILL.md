# 執筆ガイド

技術ブログ、資料、手順書、README など、書き物に共通する文体のルール。各プロジェクトの設定ファイルにある固有のルールと併せて使う。

## 使い方

書く前にこのガイドを読み、書いた直後に「書き終えたら見る10項目」と機械検査を通す。提案段階の下書きや、短い紹介文も対象にする。短い文ほど締めの一文が目立つ。

## 書き終えたら見る10項目

1. **段落末のまとめ直し**。説明を終えた直後に「これが◯◯の形です」と抽象的な言葉で包み直す一文を足さない。言い終えたら、そこで終える。
2. **「効く」**。比喩としての「効く」「効いてくる」は使わず、何がどうなるかを具体的に書く。
3. **ダッシュ**（`—` `──`）による区切り。読点で区切るか、文を分ける。
4. **体言止めの列挙を句点で締める**形（「〜する会議のメモ。」）。文として言い切るか、「〜など」で受ける。
5. **こなれた比喩の動詞**（仕込む、拾ってくれる、地続き、一撃で）。起きたことを具体的な動詞で書く。
6. **長すぎる段落**。囲みの中でも、話題が変わるところで改行する。
7. **AI の挙動の断定**。やり方が複数ありうるものを、一通りに言い切らない。
8. **箇条書きの行頭を「太字のラベル＋コロン」で始める**形。1段落で書ける内容なら、箇条書きをやめて地の文に戻す。並列の項目が4つ以上あるなら、ラベルを外した箇条書きにする。
9. **成果物への絵文字**。見出しの頭やアイコン代わりに付けない。
10. **主文のあとの否定の但し書き**（「〜を編集します。外部には何も送りません」）。読み手が心配していない副作用は書かない。範囲を伝える必要があるときは、主文の中に肯定形で書く（「手元の〜を編集します」）。

1番だけは決まり文句が無いので、段落の最後の文を1つずつ読み、削っても失われる情報が無いかで判定する。残りは機械で拾える。

```bash
rg -n '効[くきい]|効か|—|──|地続き|一撃で|仕込[みむ]|拾ってくれ|劇的に|驚くほど|構いません' <file>
rg -n '^\s*[-*] \*\*' <file>
rg -n '[\x{1F300}-\x{1FAFF}\x{2600}-\x{27BF}]' <file>
rg -o -N '[^。「」]{0,40}(ません|だけです|のみです)。' <file>
```

この語の一覧は完全ではない。指摘を受けたら足していく。プロジェクトで正式に採用した用語は、一覧に当たっても対象外にする。

## AI臭さは文の長さではない

下の一覧は表現の禁止であって、「短く書け」という指示ではない。語を足して日本語として自然になる推敲は改善になる。

| Before | After |
|---|---|
| 設定を見て直します | 設定ファイルの値を確かめてから直します |
| 表示は正常なので気づけません | 画面の表示は正常に見えるため、データが古いことにすぐには気づけません |

迷ったら声に出して読み、自然なほうを選ぶ。

## 避ける表現

| 避けるもの | 理由と代わりの書き方 |
|---|---|
| 太字の多用 | 本当に強調が要る箇所だけにする |
| 無生物主語の直訳調（「使いすぎは待ち時間として現れる」） | 人や動作を主語にする（「使いすぎると、待ち時間が増えます」） |
| 「項目名：説明」の並び、見出しのコロン | 地の文で書くか、見出しの階層で分ける |
| 「〜することができます」 | 「〜できます」 |
| 「〜を活用する」の繰り返し | 「使う」 |
| 「〜についてご紹介します」で始める | いきなり本題に入る |
| 比喩のキャッチフレーズ（「持ち運べる仕事術」） | 具体的な状況で言う |
| 短い句を重ねて短く言い切る締め（「大事なのは、◯◯です」） | 普通の長さの文で終える |
| 敬体の文章に、常体の短い言い切りを差し込む | 敬体で通す |
| 説明のための造語（「◯◯らしさ」「◯◯性」で概念に名前を付ける） | 何が違うのかを文で説明する |
| 「これを◯◯と呼びます」という命名 | 名前を付けず、そのまま説明する |
| 効果を盛る副詞（劇的に、驚くほど、一気に） | 数字か、何が減るのかで書く |
| 動詞を3つ並べたラベル（「考える、動く、振り返る」） | 地の文で流れを説明する |
| 決め台詞の使い回し（「〜の正体」「〜こそ」「本丸」） | 1つの文書で2回まで |
| 対句の標語（「使いながら守り、守りながら使う」） | 説明の文にする |
| 許可の言い回し（「〜でも構いません」） | 「〜で大丈夫です」か、言い切る |
| 見出しの売り文句（「〜だけ」「〜が変わる」） | 節の内容を示す名詞にする |

構成でも、短い文章への目次、読めば分かる「まとめ」の節、漏れなく並べただけのリスト、毎回の「以下のとおりです」＋箇条書きを避ける。

## 説明の組み立て

### 用語

- 語注が要るかは、その語を専門外の同僚が会話で使うかで決める。業界で日常語になったカタカナ語ほど取りこぼしやすい。
- 語注を足す前に、その語を使わずに書けないかを考える。
- 平易な言葉に言い換えた機能は、初めて出るところで正式名称を1回だけ添える。
- 語注はその語が初めて出る場所に置く。通りがかりに出るだけの文では、その語を使わない。
- 語注の中身は辞書の定義ではなく、その文脈で読み手に要る意味にする。
- 1つの文に括弧書きは1つまでにする。
- 略語は初めて出るところで展開し、何をするものかを1行添える。
- 製品名はカタカナにせず、正式な表記のまま書く。

### 例示

- 例は、読み手が自分の状況に置き換えられる粒度で選ぶ。複数並べるなら、1つずつ別の要点を表すものにする。
- 例文が現実の仕事の流れとして成り立つかを、文体とは別に読み直す。
- 同じ例を離れた場所で繰り返さない。

### 数字

- 所要時間や効果の数字は、測ったものだけを書く。
- 数字には出所を一言添える（「手元の計測では」）。
- 「どれでも」「必ず」のような全称の限定を外し、限定の無い肯定文にする。

### 段落

- 段落が長くなったら、「ただし」「なお」で話が変わるところで分ける。
- 1〜2文の短い段落を続けない。
- 同じ文末を3回続けない。
- 図は、その図を説明する段落の直後に置く。

### 読み手への態度

- 読み手になりうる人（経営層・管理部門・取引先）を批判の調子で書かない。相手の意図をまず認め、その意図をかなえる方法として書く。
- 読み手の今のやり方を、感情的な語でけなさない。
- 読み手にしてほしい操作は「〜しましょう」で書く。ただし続けすぎない。

## 表記

- インラインコードの前後に半角スペースを入れる。コードブロックには言語を指定する。
- 動作の主体が曖昧な受け身を避ける（「設定される」→「ユーザーが設定する」）。
- 日本語の太字は、全角の約物の手前で切る（`**前者**（冒頭）を採る` の形）。約物を太字の内側の端に置くと、`**` がそのまま表示される。
- 箇条書きの行頭に「・」を使わない。本文中の並列の中点と区別がつかなくなる。
- 長い日本語を書いたら、ほかの言語の文字が紛れ込んでいないかを機械で確かめる。

```bash
rg -n '[가-힣Ѐ-ӿ]' <file>
```

## README

- 見出しは機能の名前（主な機能、セットアップ、使い方の例）にする。
- 冒頭は「◯◯は、〜するツールです」の説明文から始め、キャッチコピーの引用を置かない。
- 形は情報の性質で選ぶ。並列の条件が4つ以上なら箇条書き、3つ以上を同じ観点で見比べるなら表、理由や仕組みは地の文、順番に行う操作は番号リスト。
- 動かす前に知らないと困ることだけを書き、内部の細部は書かない。
- 地の文にインラインコードを散らさない。コマンドはコードブロックにまとめる。
