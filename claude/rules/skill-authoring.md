# スキル作成・更新ルール（全プロジェクト共通）

`.claude/skills/<name>/SKILL.md` を新規作成または編集するときの共通ルール。ユーザースコープでもプロジェクトスコープでも同じ方針を適用する。

## frontmatter に `model` は書かない。軽くしたいスキルは `effort: low`

スキルの `model` は、そのターンの残りを会話全体ごと別のモデルで走らせる。キャッシュはモデルごとに別なので会話全体の読み直しが発生し、Opus 5.5 の思考ブロックは Fable 5.1 以外のモデルに読めないので直前までの考えも引き継がれない。`model: opus` は Fable 5.1 のセッションでは格下げにもなる。だからモデルはセッションのものを引き継ぎ、軽さは同じモデルのまま `effort` で調整する。

| スキルの性質 | frontmatter |
|---|---|
| 判断をほぼ含まない定型作業（同期・publish・一覧取得・ページ数の計測など） | `effort: low` |
| それ以外（ナレッジ参照・トラブルシューティング・文章・設計判断） | 何も書かない（セッションの effort を引き継ぐ） |

```yaml
---
name: <skill-name>
description: <発動条件が明確な説明>
argument-hint: [<引数ヒント>]
effort: low   # 定型作業のスキルだけ
---
```

`context: fork` でサブエージェントとして走らせるスキルは会話を引き継がないので、この理由は当てはまらない。そこでは読むだけの重い下請けに軽いモデルを指定してよい。

既存スキルを編集するついでに frontmatter を見て、`model` が残っていれば外す。

## スキル設計時のコンテキスト配慮

スキルが大量出力（`git diff`・jq 結果・長いファイル群・ログ等）を扱うときの設計指針。大規模出力の一般的な扱い・subagent 委譲・並列起動の失敗パターンは [`development.md`](development.md) を参照。ここではスキル設計固有の点だけ：

- **SKILL.md は短く保つ**（100行以下目安。超えるなら別ファイルへ切り出し）
- **重い処理は `scripts/foo.sh` に切り出す**（シェルスクリプト内部の出力は親 context に流入しない）
- **長い subagent プロンプトは `prompts/foo.md` に切り出し**、起動時に `Read` で読み込む
- **規模判定すら親でやらない**（`git diff --stat` も出力肥大の元。最初から無条件で subagent / scripts に委譲）

| スキル種別 | 推奨設計 |
|----------|---------|
| 単純な情報取得・状態確認 | SKILL.md 内に bash 直接記述で OK |
| 大量出力を扱う（diff/log/jq） | scripts/ に切り出し、SKILL.md は呼ぶだけ |
| LLM 判断＋大量入力 | subagent 委譲、戻り値は構造化（JSON 等） |
| 複数言語/環境の同期処理 | scripts/ 内で完結（subagent 不要） |

> **設計だけでは context 限界は防げない**。長い会話＋MCP 大量ロード時はスキル本文の展開だけで超過しうる。重いスキル（`/commit-push` や設定同期系など）は **`/clear` で新セッションにしてから呼ぶ**のが最終対策。
