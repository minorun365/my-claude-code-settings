# 開発ルール（言語・シェル・OS 固有の罠）

`AGENTS.md` の「開発ルール」節の詳細版。**どれも「エラーにならずに間違った結果を返す」タイプの罠**で、成功したと誤読したまま先へ進むのが共通の被害になる。

## ブラウザ操作

profile の分離とタブの所有権（自動操作は専用 profile で行い、自分が作っていないタブを触らない）は `AGENTS.md`「Chrome profile」節が正本。ここでは操作の技術的な罠だけを置く。

### 自作 HTML の描画検証は `file://` ではなくローカル HTTP サーバーで開く

ブラウザ拡張系のツールは `file://` を受け付けず、**`https://file:///...` へ書き換えて開こうとする**ものがある。エラーにならず、真っ白なページを「開けた」と誤認しやすい。自分で作った HTML を確認したいときは、そのディレクトリで簡易サーバーを立てて `127.0.0.1` 経由で開く。

```bash
(cd <html のあるディレクトリ> && python3 -m http.server 8931 >/dev/null 2>&1 &)
```

確認が終わったら `pkill -f "http.server 8931"` で止める。

- ページ内アンカー（`#section`）の動作を試すときは、**URL に同じハッシュが付いた状態でリンクを押しても何も起きない**。ハッシュなしの URL で読み込み直してからクリックする
- `scrollIntoView({behavior:"smooth"})` は非同期なので、クリック直後のスクリーンショットはスクロール途中の空白域が写る。1〜2 秒待ってから撮る

### `127.0.0.1` は全プロジェクト共通のオリジン。別プロジェクトの Service Worker が検証結果を汚す

ポート番号が違えば別オリジンだが、**同じポートを再利用すると、前に検証した別アプリの Service Worker が生き残っていて、API レスポンスまでキャッシュから返す**。検証を始める前に必ず確認して掃除する。

```javascript
(await navigator.serviceWorker.getRegistrations()).length   // 0 でなければ汚染されている
```

0 でなければ、全登録を `unregister()` し `caches.keys()` を全削除してから読み込み直す。**`fetch` に `cache:'no-store'` を付けても SW の fetch ハンドラーは迂回できない**ので、no-store を根拠に「キャッシュではない」と判断しない。

症状の見分け方は、**GET だけ古い値が返り、POST / DELETE は通る**（SW は通常 GET しかキャッシュしない）。切り分けはサーバー側にリクエストログを出すのが最短で、**ブラウザーの GET がサーバーのログに現れなければ SW が答えている**。レスポンスにサーバーの PID などの識別子を入れておくと一撃で確定する。

削除や更新が画面に反映されないとき、原因を自分のコードだと決めつける前に、検証環境が嘘をついていないかを疑う。

### クリックは座標ではなく要素参照（`ref`）で行う

**フォームの選択肢・ボタンを押すときは、スクリーンショットを見て座標を渡すのではなく、ページ読み取りが返す要素参照を使う。**

スクリーンショットは実ビューポートを拡大して返すことがあるため（例: 924×943 が 1092×1115 で返る＝約1.18倍）、**スクショ上で読み取った座標と実ページ座標がずれる**。ずれ方が一定でないので当たる要素と当たらない要素が混在し、しかも**押せていないだけなのかクリック先を間違えたのかが画面から判別できない**。ズーム機能の範囲指定が実ビューポート座標系で解釈される場合、狙った要素が写らないことが座標系のずれの決定的な証拠になる。

- ページ読み取りの「操作可能な要素だけ」フィルタは**ビューポート内の要素しか返さない**。長いフォームはスクロールしてから読み直して参照を採り直す
- 参照 ID の連番から未取得の要素を推測してクリックしない（並び順の思い込みで別の項目を送信する事故になる）
- 座標クリックが必要な場面（参照が付かない canvas 等）では、**1クリックごとにスクリーンショットで結果を検証**する。複数クリックをバッチに並べると、どのクリックが外れたか切り分けられなくなる
- 広告が挿入されるページでは、クリックの合間にレイアウトが動く。座標クリックだと**広告を踏んで別タブが開く**

**足し算式のフォームに注意する。** 初期値が全項目「不可」で、可にしたい項目を押していく形式のフォームでは、**押し忘れがそのまま「不可」として登録される**。送信前に、入力した項目数と対象項目数を数えて突き合わせる。

### `screencapture` は必ず範囲指定で撮る

**引数なしの全画面撮影をしない。** ユーザーは並行して自分の作業をしているので、メール・チャット・業務資料の中身がそのまま写る。見る必要のない情報を読み込むことになり、機密の観点でも良くない。

```bash
screencapture -x -R0,0,1710,30 out.png   # メニューバーだけ
```

- `-x` はシャッター音を鳴らさない。**常に付ける**
- `-R x,y,w,h` は**論理座標**（Retina では撮影結果が2倍のピクセル数で返る）。範囲がずれたら、返ってきた画像サイズと指定幅の比からスケールを割り出して計算し直す
- **アプリのウィンドウだけを撮りたいが位置を特定できない場合は、撮影自体を諦める。** ウィンドウ位置の取得にはアクセシビリティ権限が要り、無音のダイアログを踏む。ユーザーに画面を見てもらうほうが速くて安全
- 誤って撮ってしまったら、**その場でファイルを削除し、写っていた内容には触れない**

## サブエージェントとコンテキスト

### 大規模出力を親コンテキストに取り込まない

`git diff` 生パッチ・大量 grep 結果・PDF 全文・長大ログ等を親のメッセージ履歴に直接流し込まない。親の膨張は後続ツール呼び出しやサブエージェント起動プロンプトに波及し、MCP 定義が重い環境では特に上限超過しやすい。

| 出力の目安 | 処理方針 |
|-----------|---------|
| 500 行未満 / 数十KB 以下 | 親で直接読んで OK |
| 500 行以上 / 数百KB 以上 / 数十ファイル分の diff / PDF 30ページ超 | サブエージェントに委譲し、要約・判定結果（表・JSON）だけ受け取る |

サブエージェント委譲の作法:

- プロンプトは**自己完結**で書く（「親のコンテキストを参照」と書かず、必要な情報・ルールを再掲する）
- 戻り値はフォーマット固定（JSON / 表）にして生データを返させない。並列時は戻り値の合計サイズも指定する（例：上位 N 件・1件200字以内）
- 編集・コミット等の副作用のある操作は親が担当し、子は読み取り・分析に限定する

**メールスレッド取得系の API は特に大容量化しやすい。** 添付込みの長いスレッドは数 MB 級になり、トークン上限で失敗する。失敗時にファイルパスが示されるなら、その JSON を Bash 上の Python で解析する。

- 各メッセージの本文は**返信元の全文引用**を含むため、素朴なキーワード grep はノイズだらけになる。引用開始行（`^>` や `^\d{4}年\d{1,2}月\d{1,2}日` の日時ヘッダ）より前だけを「新規本文」として切り出してから絞り込む
- 検索 API はスニペットベースなので、表記ゆれや長いスレッドの後半を取りこぼす。経緯を追うときは、まず全メッセージの日付・送信者一覧を出し、次に新規本文だけのキーワード抽出という2段構えにする

### 並列起動は原則逐次

「MCP 定義が重い環境 × 親コンテキストの膨張 × 複数並列」が揃うと、プロンプト長超過で即失敗する。

対策の優先順は、①並列をやめて逐次処理（完走確実性優先）②親のコンテキストを事前に軽くする ③子に渡す prompt を簡潔にする ④どうしても並列なら 2〜3 個まで。

スキルで並列起動を設計するときは、SKILL.md に「並列化できる根拠」を明記する。根拠がなければデフォルトで逐次。

### 「調べつくして」を規模の白紙委任と読まない

「調べつくして」「徹底的に」「網羅的に」「全部洗い出して」は**徹底度の指示であって規模の指示ではない**。高性能モデルのセッションでこれを字義どおり受けて大量並列を撒くと、子は親と同じモデルを継承するため**トークン消費が桁で膨らみ、レートリミットに当たってセッションごと止まる**。

- **4体以上のサブエージェント起動、または多段オーケストレーションを始める前に、計画の規模を1〜2行で提示して確認を取る**（例:「観点5系統×検証2巡で最大15エージェント回します。消費が大きいですが進めますか？ 逐次3体の縮小版もあります」）。3体以下の逐次・小規模並列は確認不要
- 確認なしで進めてよいのは、**ユーザーが規模を明示したとき**だけ
- 機械的な収集・整形ステージは軽量モデルへ落とし、親モデル継承のまま撒かない
- レートリミットに当たってからの分割リトライは、消費をさらに積むだけなので回復手段にしない。当たったら残作業を報告して指示を待つ

## 一括置換の事故

### perl / sed の `|` エスケープ漏れ

`perl -pi -e 's/| foo | bar |/.../'` のように**パターン先頭・中間の `|` を未エスケープ**にすると、正規表現の交替（alternation）として解釈され**空文字列にもマッチ → 全行の行頭に置換文字列が挿入**される大事故になる。

- Markdown テーブル行など `|` を含む置換は **`\|` に全てエスケープ**するか、**エディタツール / Python スクリプトを使う**
- **一括置換後は必ず `head` / `git diff` で対象ファイルの構造を目視確認**する。置換の exit code だけで成功と判断しない
- **「意図した箇所以外は1文字も変わっていない」を機械で証明する。** 目視は差分が多いと破綻する。置換対象（コメント・タグ等）を正規表現で除去して正規化したテキストを、`git show HEAD:<path>` の版と全ファイル比較し、差分ゼロを確認する。これなら数十ファイル・数百行の変更でも巻き込み事故を確実に検出できる
- 複数ファイルへの機械置換後は「同一行頭が多数行で繰り返される」「テーブル断片と見出しが同一行に混在」等の壊れパターンを grep で検査する

### JS の `String.replace()` は文字列パターンだと最初の1回しか置換しない

テンプレートのプレースホルダを埋める処理で `code.replace('__TOKEN__', value)` と書くと、**ファイル内の最初の1箇所しか置換されない**。とくに**テンプレート冒頭の説明コメントにプレースホルダ名そのものを書いている**と、置換がコメント側に吸われ、本体は未置換のまま残る。

- **`replaceAll()` を使う**か、正規表現に `/g` を付ける
- **テンプレートの説明コメントにプレースホルダ文字列そのものを書かない**。「下の TOKEN 定数に差し込まれる」のように、リテラルを避けて説明する
- **置換後にプレースホルダ残存を検査して throw する**。これが無いとビルドもデプロイも成功してしまい、「なぜか常に 403」のような分かりにくい形でしか表面化しない
- 生成物が正しいかは、デプロイ前に生成ファイルを機械チェックする（`grep -c '__'`、期待値との突き合わせ）

## シェルの罠

### zsh の glob 失敗はコマンド全体を中断させる（検証の偽陰性）

zsh はマッチしない glob（例: `references/*.md` が存在しないディレクトリ）があると `no matches found` で**コマンド全体を実行せず中断**する。`2>/dev/null` では防げない。grep 検証にこれが混ざると「grep が実行されなかった」のに「マッチなし＝存在しない」と誤判定する偽陰性事故になる。

- 存在が不確かなパスの glob は使わず、**ディレクトリごとに個別実行**するか `grep -r <dir>/` でディレクトリ再帰にする
- どうしても glob を使うなら `setopt null_glob` か `ls <glob> 2>/dev/null` で先に存在確認する
- **「無い」と断定する前に、検証コマンド自体が実行されたか（エラー出力の有無）を確認する**

同系統の罠が2つある。

- zsh は `=` で始まる裸のワードを `=command` 展開（コマンドのパス解決）するため、`echo ===` のような区切り線出力が `== not found` で**コマンド全体を中断**させる。区切り線は `echo "==="` とクォートするか `---` を使う
- `grep -rn … --include=*.md` のように**オプション値の glob を裸で書く**と zsh が展開を試み、`no matches found: --include=*.md` でコマンド全体が中断する。`--include='*.md'` とクォートする

### `cmd | tail` の exit code はパイプ最後のコマンドのもの

デプロイ・ビルド・テストなど成否が重要なコマンドを `| tail` や `| head` で絞るときは、必ず `set -o pipefail` を付ける。付け忘れると**失敗を exit 0（成功）と読み違える**。デプロイが失敗してロールバックしていても、通知上は「完了（exit 0）」と出る。

### `rg` のフラグをまとめ書きするとき `-r` を混ぜない

`-r` は `--replace` であって「再帰」ではない。`rg -rn 'pat' dir/` は `-r n` と解釈され、**マッチした部分を `n` に置換した結果を表示する**。`rg -ril 'pat'` も同様に `-r il` になる。

エラーにならず検索自体は成功するので気づけない。しかも**置換されるのは探していた語そのもの**なので、結果を読んだ側は固有名詞や識別子を取り違える。`rg` は既定で再帰検索なのでそもそも `-r` は要らない（`-i` 大小無視・`-l` ファイル名のみ・`-n` 行番号だけを渡す）。**検索結果に見覚えのない短い綴りが混ざったら、置換されたと疑う。**

### macOS の bash 3.2 固有の罠

macOS 標準の bash は 3.2 系なので、Linux で検証すると再現しない罠がある。`set -euo pipefail` を付けたスクリプトほど本番直前で落ちる。

**① 全角文字の直前の変数展開が壊れる。** `echo "期限: $EXPIRES（30日）"` のようにマルチバイト文字が続くと、bash 3.2 がそれを変数名の一部として読み、`set -u` 下で「未割り当ての変数です」で落ちる（`set -u` が無いと黙って空文字になる方が厄介）。日本語を含むスクリプトでは必ず `${VAR}` とブレースで囲む。書いた直後に機械検出できる。

```bash
rg -n '\$[A-Za-z_][A-Za-z0-9_]*(?=[^\x00-\x7F])' <file>
```

**② 空の配列を `"${arr[@]}"` で展開すると `set -u` 下で `unbound variable` になる。** 「条件が成り立つときだけオプションを足す」用途で配列を使うと必ず踏む。`${arr[@]+"${arr[@]}"}` と書けば、空のときは何も展開されず安全（bash 4 以降は素の書き方でも動く）。書いた直後に空の状態で1回流して確かめる。

### macOS の `date -jf` は入力文字列をローカルタイムとして解釈する

API が返す UTC タイムスタンプ（`...Z`）をそのまま渡すと、`TZ=Asia/Tokyo` を付けても変換されず**9時間ずれた JST として表示される**。

```bash
EPOCH=$(TZ=UTC date -jf "%Y-%m-%dT%H:%M:%SZ" "$T" +%s)
TZ=Asia/Tokyo date -r "$EPOCH"
```

期限・締切を扱うときは既知の値で必ず検算する。

### jq の `\(...)` 文字列補間と bash の衝突

jq の文字列補間 `"\(.field)"` を**二重引用符**の jq フィルタに入れると、bash が `\` を消費して `syntax error, unexpected INVALID_CHARACTER` になる。

- **jq フィルタはシングルクォートで囲む**：`jq -r '"- name: \(.name)"' "$f"`
- フィルタ内で bash 変数が必要ならヒアドキュメントで渡す
- 複数の補間や複雑な join は最初から Python に切り替える（シェルクォート地獄を回避）

## パッケージ管理

### グローバル npm パッケージを一括更新したら1本ずつ検証する

インストールの exit 0 は「動く」を意味しない。対象コマンドを `--version` で叩いて確かめる。

とくに `corepack` を更新すると、corepack が bin として宣言している **`pnpm` / `pnpx` / `yarn` / `yarnpkg` のシンボリックリンクを奪う**。シムは実行時にパッケージをダウンロードしようとして**対話プロンプトで止まる**ため、コマンドが事実上使えなくなる。直し方は `corepack disable` でシムを外してから `npm i -g pnpm@latest` で貼り直す。**`corepack disable` は yarn のシムも消す**ので、yarn を使っているなら別途入れ直す。

Homebrew の node formula に `npm` と `corepack` が同梱されている場合、`brew list <name>` で探しても出てこない。formula 名で見つからないものは npm グローバル管理を疑う（実体は `/opt/homebrew/lib/node_modules/`）。

## 複数作業の混線防止

- Bash の並列実行間でも **working directory は共有される**。片方の `cd` がもう片方の git 操作先を変えてしまう。`cd` を使わず **`git -C <path>`** でリポジトリを明示し、異なるリポジトリの更新を同一メッセージで並列にしない
- `git add -A` / `git add <dir>/` / `git add -u <dir>/` は**並行セッションの未コミットファイルを巻き込む**。`-u` は「追跡済みだけだから安全」に見えるが、ディレクトリ指定なら巻き込み方は同じ。対策の優先順：
  1. 自分が触ったファイルパスを明示列挙して add する
  2. `git commit <path> -m "..."` でパス指定コミット（**`git add` で明示列挙した場合に限る**。下記の `git apply --cached` で絞った直後には使わない）
  3. コミット前に `git status --short <dir>/` で目視。見覚えのないファイルは別セッションの作業
  4. `git add -A` 系は「自分しか触っていない」と確信できるときだけ
  5. 削除を stage したいときも `git add <消したファイルの明示パス>` で足りる

### 共有台帳ファイルはパスを明示列挙しても巻き込みを防げない

複数セッションが同じファイルへ1行ずつ足す種類のファイル（登録リスト、案件の索引 `README.md`、集計用 YAML など）は、ファイル単位で stage する以上、他セッションの未コミット行も一緒に入る。**この種のファイルは、add の直前に `git diff <path>` を読んで自分の変更だけかを確かめる。**

混ざっていた場合、`git add -p` は対話式なのでエージェントからは使えない。**`-U0` で行単位のハンクに割ってから、自分のハンクだけ `git apply --cached` する。**

```bash
git diff -U0 <path> > /tmp/all.patch   # 文脈行なし＝変更行ごとに別ハンクになる
# ヘッダー（--- / +++ まで）＋ 自分のハンクだけを抜き出して /tmp/mine.patch を作る
git apply --cached --unidiff-zero /tmp/mine.patch
git diff --cached <path>                # 自分の変更だけが stage されたか目で確認
```

**既定の `git diff`（文脈3行）だと、近い行の変更が同一ハンクに合流して分離できない。** 必ず `-U0` を使い、`git apply` 側にも `--unidiff-zero` を付ける。分離できなければ、そのファイルは**コミットせず相手に委ねる**。無理に含めて報告するより、触らないほうが後始末が要らない。

**`git apply --cached` で index を絞った直後に `git commit <path> -m "..."` を打つと台無しになる。** pathspec 付きの `git commit` は index を見ず、その時点のワーキングツリーの内容をそのままコミットするため、絞ったはずの index が無視され、他セッションの未コミット分を丸ごと巻き込む。この直後は pathspec を付けない `git commit -m "..."` を使う。

```bash
git apply --cached --unidiff-zero /tmp/mine.patch
git diff --cached <path>   # 自分の変更だけが stage されたか確認
git commit -m "..."        # ← ここで <path> を付けない。付けるとワーキングツリー全体に戻る
```

**確認の `git diff` と `git add`〜`commit` を、同じ連結コマンド（`&&` つなぎ）に入れない。** 連結すると diff の出力を読む前に add が走り、「確認したつもりで巻き込む」形になる。diff は単独で実行して出力を読み、自分の変更だけと確かめてから次のコマンドで add する。

確認は「毎回」に固定する。同じセッションで2回うまくいったから3回目は省く、という省き方で踏む。
