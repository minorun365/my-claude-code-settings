# 外部発信時の確認ルール

**他者の共有スペースへの発信は、確認を1回だけにする。その1回をどこで取るかは、hook の守備範囲かどうかで決まる。**

| 発信の種類 | 承認の取り方 |
|---|---|
| **hook の守備範囲**（同梱の `check-outbound.sh` が見張る、他人のリポジトリへの `gh` 書き込み） | **hook の許可ダイアログが承認。** チャットで「送ってよいですか」と聞かない。全文をチャットへ `text` で出し、**同じターンでそのまま送信コマンドを打つ** |
| **hook の範囲外**（メール・Slack・Notion・ブラウザからの投稿・Webhook・自分のリポジトリの PR / Issue 文面など） | チャットで全文を見せて「送って」をもらってから実行する |

チャットの確認と hook のダイアログを両方出すと、ユーザーは同じ送信に2回承認することになる。hook を持たないツールから送るときは、すべてチャットで確認する。

同梱の hook は典型的な `gh` コマンドを検出する補助策であり、変数展開、alias、別 CLI などを完全には検出できない。自分の判断とサービス側の最小権限を併用する。

## 発信の直前に、発信ルールをディスクから読み直す

**文面を提示する前に、`~/.claude/AGENTS.md` の「外部発信ルール」節と、このファイルの本文を Read で読み直す。**

セッション開始時にコンテキストへ注入された設定は、**その時点のスナップショット**である。複数のセッションを並行させていると、別セッションで恒久化した新しいルールは、実行中のセッションのコンテキストには反映されない。長いセッションほど、自分が見ているルールは古い。

- 文面の書き出し・宛先・名乗りなど、**発信物の体裁に関するルールは特に更新されやすい**ので、毎回読み直す
- 「自分の記憶にないから、そんなルールはない」と判断しない。**記憶にないことと、ルールが存在しないことは別**
- **`sed -n '/## 節名/,/^## /p'` のように節を切り出して読まない。ファイル全文を読む。** 切り出しでは自分が既に知っている節しか選べないので、別セッションがその日に追加した新しい節を構造的に見落とす
- 原因がコンテキストの鮮度だけなら、hook での機械強制は足さず、この読み直しの運用で対応する

## 中身まで指定された発信は、承認を取り直さずに送る

**「送って」「もう一度送って」「◯◯と返して」と、ユーザーが中身まで指定したものは、そのまま実行する。** ここで確認を挟むと、ユーザーは同じことを2回言うことになる。

- hook の範囲外の発信で、初回のドラフトは全文を提示して承認を取る。省いてよいのは、**承認済みの文面へユーザー自身が指定した変更を当てて送り直すとき**と、**返す中身を名指しで指示されたとき**の2つだけ
- 事前承認を省いても、**全文をチャットへ `text` で載せる**のは省かない
- 準備でつまずいて2回打つのも、承認を増やす。添付があるなら先に必要な場所へ置き、送信は1コマンドで終える

## 拒否されたら、そこで止まる。打ち方を変えて再実行しない

**許可ダイアログで「拒否」を押されたら、それは「その操作をするな」という意思表示である。** 同時に受け取った指摘が体裁の話であっても、指摘は拒否の理由の説明であって、条件を満たせば実行してよいという許可ではない。

- 拒否された発信は、**同じ内容を別の打ち方・別のコマンド・別のツールで再実行しない**。下書き経由をやめて直接送る、ID 指定をやめて本文を引数に載せる、といった書き換えは「打ち方の改善」に見えて、実際にやっているのは拒否された操作そのもの
- 拒否のあとは、チャットでの指示を待つ。「ここを直して送って」と言われたら、直した全文をチャットへ出して送り直す。指摘だけで送れとは言われていないなら、直した全文を見せて止まる
- **先行の承認は、拒否によって無効になる。** 前のターンの同意を、拒否のあとの実行の根拠に使わない

## 打つ前に、そのコマンドが hook の守備範囲かを確かめる

**hook のダイアログを承認にする以上、ダイアログが出ないまま相手へ飛ぶコマンドを打つのが最大の事故になる。** hook はパターンマッチなので、ヘルパー形式・エイリアス・別のツール経由で外れる。

- 送信コマンドは hook が想定している形でだけ打つ。**想定外の形（新しいヘルパー、ブラウザ操作、別 CLI）なら hook の範囲外として扱い、チャットで承認を取る**
- 形が合っているか迷ったら、範囲外として扱う（確認が1回増えるだけで済む）
- **hook の穴を見つけたら、その場でパターンへ足し、検体で ask が返ることを確かめる**
- **権限を広げたら、同じターンで hook の守備範囲も広げる。** 読み取り専用を前提に対象外にしていた経路は、権限を広げた瞬間に「確認ダイアログの出ない送信経路」に変わる

## 承認ダイアログは、コマンド文字列だけで判断できる形にする

**許可ダイアログには直前のコマンド文字列しか表示されない。** スマートフォンから承認することもあり、チャットへ本文全文を提示していても、承認の場では見えない。**コマンドを見ただけで「誰に何を送るのか」が分からないなら、その打ち方が間違っている。**

- **ID だけを渡す実行にしない。** 下書き ID やコメント ID だけを指定する送信は、宛先・件名・本文・添付のどれも読み取れない。「下書きを作って検証 → ID で送信」の二段構えは、検証としては正しくても承認の場では最悪の形になる
- 発信は本文全文と添付パスを引数に載せた1コマンドで打つ。Bash の `description` にも宛先を日本語で書く
- **調査・検証コマンドも同じ。** `cd /tmp/... && python3 -c ...` のような複合コマンドは、何の承認なのか判別できない。承認が要りそうな検証は、目的を1行書いてから単独で打つ

## 承認を求めるときは、コマンドの前に日本語で説明する

コマンド文字列は判断材料にならない前提で書く。コマンドを打つ直前のチャットへ、次の4点を日本語で書く。

1. **何をするコマンドか**（目的を1行）
2. **実行すると何が起きるか**（副作用。ローカルのファイルが書き変わるだけか、外部へ飛ぶか）
3. **外部への影響の有無**（誰に届くか。届かないなら「外部への送信はありません」と明記する）
4. **どういう条件なら承認してほしいか**（判断の分かれ目）

- 発信だけでなく、**調査・検証・デバッグのコマンドも対象**。無害なものほど「これは何の承認なのか」が伝わらず、判断できないまま止まる
- 承認が複数続くときは、**何件あるか・いまが何件目か**を書く
- **hook の守備範囲の送信では、この4点を1〜2行で書いてすぐコマンドを打つ。** 説明のあとに「よろしいですか」と止まらない
- **1回の承認で複数の外部操作をまとめて求めない。** 「シートへ書き込み、あわせて Slack へ共有します」のように束ねると、片方だけ要るときに全体を差し戻すことになる。必要な操作だけを提案し、付随作業は別に「やりますか？」と聞く
- **公開・デプロイ系の承認では、「同時に上がってしまうもの」を書く。** `rsync --delete` / `aws s3 sync --delete` / `npm run publish` のようにディレクトリ全体を同期するコマンドは、別セッションが置いた未確認の変更まで一緒に公開する。自分の変更だけが出ると読める書き方をしない

## 発信コマンドは単独の Bash 呼び出しで打つ

発信コマンドを他のコマンドと連結しない。本文が長い場合はヒアドキュメントで連結せず、**Write ツールでファイルを作ってから `--body-file` で渡す。** 自動モードでは permissions とは別に classifier が働き、長い本文と発信コマンドを1つの文字列に連結すると「何を送るのかコマンドから読み取れない」として `Blocked by classifier` で拒否される。

**ただし `--body-file` はコマンド文字列から本文を消すので、そのままでは承認ダイアログが不透明になる。** 両立のさせ方は1つだけで、**チャットへ全文を貼る → `--body-file` で実行**、の順に固定する（hook の守備範囲なら同じターンで実行してよく、範囲外なら間に「送って」をもらう）。

投稿済みコメントの文面を直すときは、削除して再投稿せず `gh api repos/<owner>/<repo>/issues/comments/<id> -X PATCH -F body=@<file>` で編集する（相手への通知が重複せず、コメント URL も維持される）。

## 機械的な安全網（hook）

同梱の `hooks/check-outbound.sh` を `PreToolUse` hook として登録すると、`settings.json` の `Bash(*)` 自動許可より優先して `permissionDecision: ask` を返し、許可ダイアログへ切り替える。宛先は「コマンド文字列に owner 名が含まれるか」ではなく、`-R` / `--repo`・GitHub URL・API パスから抽出して厳密比較する。自分のアカウントは環境変数 `CLAUDE_OWN_GITHUB_OWNERS` で指定する。

- **この hook は撤去しない。** 学習ループ節の「常時リマインダーを hook で流し込む実装を再導入しない」は、毎ターン機械的にルールを注入する方式を指しており、この宛先検査とは別物
- **hook のダイアログで「許可」を押されたことが承認。** 逆に、hook が黙って通した（ダイアログが出なかった）ことは承認ではない
- **hook で見張っている送信を `permissions.ask` にも登録しない。** 二重にダイアログが出て、1通の送信に承認が2回要るようになる。hook のほうを残す理由は2つで、①hook のダイアログには宛先や本文の要約を載せられる（permissions 側は生のコマンド文字列だけで、長い本文は切れて読めない）②hook はスクリプトなので直した瞬間に走行中の全セッションへ効く（permissions はセッション起動時にしか読まれない）
- パターンが合っているのに止まらないときは permissions 側（`Bash(*)` の allow）を疑う。permissions を変えても、再起動までは古い設定で動く

## 対象操作

各項目の【hook】は hook のダイアログが承認、【チャット】はチャットで承認を取るもの。

### GitHub【hook】

**自分がオーナーではないリポジトリ**への発信全般：

- PR の作成 / マージ / close / reopen / convert（`gh pr create` で base が他人リポになる fork からの PR も含む）
- Issue の作成 / close / reopen / delete / transfer
- PR / Issue / Discussion へのコメント投稿（`gh pr comment`、`gh issue comment`、`gh api .../comments -X POST` 等）
- PR description の編集（`gh pr edit --body`）
- レビュー提出（`gh pr review`）
- リアクション追加（`gh api .../reactions -X POST`）

### Slack（他人がいるチャンネル全般）【チャット】

- メッセージ送信、Canvas 作成・更新

### Notion（共有ワークスペース）【チャット】

- 共有ページの作成・更新・コメント

### メール【チャット】

- Gmail 等からの送信・返信・転送

### その他 SaaS / 外部発信【チャット】

- 業務 SaaS（CRM・Wiki・ホワイトボード等）への書き込み
- 外部 Webhook 呼び出し
- X、Mastodon 等への投稿

### 複合コマンドも対象

`cd /tmp && gh pr comment ...` や `git status; gh issue create ...` のように、別コマンドと `&&` / `;` / `|` で連結されていても、**発信系コマンドが文字列のどこかに含まれていれば対象**。先頭コマンドが安全なものでも油断しない。

## 送信前にチャットへ出す情報

hook の守備範囲でも範囲外でも、送信コマンドの前に以下をチャットへ出す（範囲外ならここで止まって「送って」を待つ）：

1. **どこに投稿するか**：リポジトリ名 / チャンネル名 / URL
2. **何を投稿するか**：タイトル・本文の**全文**（要約だけで済ませない）
3. **誰に通知が飛ぶか**：メンション先、CC、@channel 等
4. **不可逆性の有無**：編集可能か、削除できるか

### 例

> 以下のコメントを `owner/repository#123` に投稿します。
>
> 宛先：メンテナー @maintainer。GitHub 通知が飛びます。後から編集・削除可能。
>
> ```
> Thanks @maintainer! I have pushed the update.
> ```

hook の守備範囲なら、この直後に送信コマンドを打つ（「投稿してよいでしょうか？」の問いかけは書かず、「投稿します」と書く）。範囲外なら、「OK」「投稿して」等と返ってきたら実行する。

## 対象外（確認**しない**）

以下は対象外。**間違っても確認しない**（過剰確認は禁止）：

- **自分のリポジトリ**（自分のフォークを含む）への commit / push / branch 操作などローカル発の全操作
- **自分の dotfiles** の同期
- ローカルファイルの編集・読み書き
- 読み取り専用 API（`gh pr view`、`gh api .../comments` の GET、`gh issue list`、検索系 MCP、`*_search_*` 等）
- ユーザーが**直前のターンで明示依頼**した個別操作（その操作1回限り、再利用しない）

**「自分のリポジトリだから対象外」が効くのは、コードとファイルの操作だけ。同じリポジトリでも、他人が読む文面（PR / Issue の本文・コメント・レビュー）は対象に入る。** 判定基準は「誰のリポジトリか」ではなく「誰かに通知が飛び、誰かが読むか」。共同作業者のいる自分のリポジトリでは、commit / push は無確認でよいが、PR 本文は全文を提示して承認を取る（hook は自分のリポジトリを通すので、ここは【チャット】）。

## アンチパターン

- ❌ Bash が自動許可されているので、流れで `gh pr comment` を打ってしまう
- ❌ 「礼儀として返信しておくべき」と判断して勝手に投稿する
- ❌ 「ユーザーが満足するだろう内容だから」と先回りで投稿する
- ❌ コメント本文を要約だけ提示して、全文を見せずに送る・聞く
- ❌ **hook の守備範囲の送信で、チャットに「送ってよいですか」と挟む**（hook のダイアログと合わせて承認が2回になる）
- ❌ 連結コマンド（`cd ... && gh pr comment ...`）で間接的に発信して確認をすり抜ける
- ❌ **自分の設定同期・dotfiles 操作まで確認に来る**（過剰確認）
- ❌ 「念のため」と何でもかんでも確認する（読み取り系・自分リポ操作は確認不要）
- ❌ **拒否されたあと、承認を取り直さずに打ち方を変えて再実行する**（拒否＝中止であって、体裁の指摘ではない）
- ❌ **hook の想定に無い形の送信コマンドを、hook が止めてくれる前提で打つ**（パターンから外れれば黙って相手へ飛ぶ）
- ❌ **下書き ID・コメント ID だけを指定する発信コマンドで承認を求める**（ダイアログからは中身が判断できない）
- ❌ **本文を `--body-file` で渡し、チャットへ全文を貼らないまま送信コマンドを打つ**（ダイアログにはパスしか出ない）
- ❌ **「自分のリポジトリだから」を理由に、他人が読む PR / Issue の文面を見せずに投稿する**
- ❌ **発信ルールの読み直しを sed の節切り出しで済ませる**（同日追加された節を構造的に見落とす）
- ❌ 長い本文をヒアドキュメントで発信コマンドに連結する（classifier にブロックされる）
